# LXFinderRight 方案设计

> Finder 右键增强工具。右键文件/文件夹可复制路径、用 iTerm 打开；右键空白处可新建各种格式的文件。
>
> 状态：方案稿，未写代码。文末「待验证清单」列出所有尚未实机确认的点。

---

## 一、结论先行

### 1.1 技术路线只有一条

**官方 Finder Sync Extension 是唯一可行的机制，没有第二条路。**

| 候选路线 | 结论 | 依据 |
|---|---|---|
| **Finder Sync Extension** | ✅ **唯一可行** | 官方 API，`FIMenuKind` 原生区分「右键文件」和「右键空白处」 |
| Accessibility 注入 | ❌ **不成立** | AX 是「读取 + 触发已有元素」的 API，**没有任何公开接口能在别的进程里新增 UI 元素**。找遍 GitHub / SO / Apple 论坛，零实现、零案例 |
| 注入 Finder 进程 | ❌ **商业上不可行** | 需用户关闭 SIP（Apple Silicon 还要进恢复模式降低启动安全策略），无法公证、无法上架，clean install 上经常注入失败 |
| Services / 快速操作 | ❌ **做不到空白处** | **右键空白处时系统会把整个 Services 子菜单删掉**；快速操作同理 |
| File Provider Custom Action | ❌ **作用域不符** | 只能出现在你自己的 provider domain 内，做不了「任意目录」 |

> 注：网上「用辅助功能往 Finder 右键菜单插项」的说法是讹传。AX 能做到的是「监听右键后弹自己的菜单」（MouseBoost 走的路），不是往原生菜单里插项——这两件事完全不同。

### 1.2 好消息：不需要敏感权限

`FinderSync.h`（macOS 26.2 SDK，版权头 `2014-2025`，**无任何 deprecated 标记**）里：

```objc
FIMenuKindContextualMenuForItems     = 0,  // 右键文件/文件夹
FIMenuKindContextualMenuForContainer = 1,  // 右键窗口空白处 ← 本产品的核心场景
```

`ContentMenuForContainer` 的注释原文是 control-clicks on the Finder window's **background**。也就是说，**「右键空白处新建文件」是官方支持的一等公民**，不需要辅助功能权限，也不需要 `LXFinderLauncher` 那套 Apple Events 自动化授权。

### 1.3 坏消息：三个硬边界（Apple 不打算修）

1. **云目录完全失效**。iCloud Drive、iCloud 同步的桌面/文稿、Dropbox / OneDrive / Google Drive 等 File Provider 路径下**不会有任何菜单**。原因是架构性的：**一个目录只允许一个扩展 "own"**，iCloud Drive 自带扩展，第三方抢不到。超级右键自己承认了这点，其 2.3.1+ 用「修饰键+右键 / 中键 / 三指点按」绕开。
2. **菜单位置和顺序不可控**。API 只允许你返回一个 `NSMenu`，没有位置参数。排不到「新建文件夹」之前，也不在「扩展」子菜单里（折叠成子菜单的是 Services/快速操作，别混淆）。排序规则 Apple 从未文档化。
3. **扩展可能被系统杀掉后不重启**，菜单就此消失，用户要去设置里关掉再开。

## 二、产品架构

### 2.1 架构结论来自三个真实产品的实证

本机已安装的三个商用 Finder 扩展，entitlements 完全一致：

| 扩展 | 沙盒 | 对用户文件的权限 |
|---|---|---|
| Beyond Compare | ✅ | 只有 `files.user-selected.read-only` |
| WPS | ✅ | 只有 `files.user-selected.read-only` |
| 百度网盘 | ✅ | 只有 `files.user-selected.read-only`（例外仅限它自己的 Application Support） |

**关键事实**：百度网盘和 Beyond Compare 的**主 App 都是非沙盒**，但它们的 `.appex` **仍然是沙盒**，而且**全都拿不到用户文件的写权限**。

由此推出两条铁律：

- **`.appex` 必须沙盒**。PlugInKit 会直接拒绝加载非沙盒扩展，日志原文 `plug-ins must be sandboxed`。所谓「官网非沙盒版」指的是主 App 非沙盒，不是扩展非沙盒。
- **扩展不该、也不能碰用户的文件**。写盘、起子进程、`NSWorkspace.open` 在扩展沙盒里全都做不了。

### 2.2 分层

```
┌─ Finder ─────────────────────────────────────────────┐
│  右键 → FIMenuKind                                   │
└────────────────────┬─────────────────────────────────┘
                     │ menu(for:)  ← 同步阻塞，只允许内存操作
┌────────────────────▼─────────────────────────────────┐
│  LXFinderRight.appex    【沙盒】                      │
│  只做两件事：渲染菜单 / 派发动作                       │
│  从 App Group 读配置（内存级）                        │
└────────────────────┬─────────────────────────────────┘
                     │ NSXPCConnection
                     │ ⚠️ 必须嵌在 appex/Contents/XPCServices/
┌────────────────────▼─────────────────────────────────┐
│  ActionRunner.xpc       【沙盒】                      │
│  接收 (URL[], 动作ID) → 交给主 App 或自己执行          │
└────────────────────┬─────────────────────────────────┘
                     │
┌────────────────────▼─────────────────────────────────┐
│  LXFinderRight.app      【非沙盒】                    │
│  Developer ID + 公证                                  │
│  设置界面 / 真正的文件操作 / 用户文件读写              │
└──────────────────────────────────────────────────────┘
```

**三个必须记住的坑**：

1. **XPC service 必须嵌在 appex 自己的 `Contents/XPCServices/` 里**，不能嵌在主 App 里。嵌在主 App 里的，appex 连不上——而且是**静默失败，没有任何报错**。Apple DTS 原话：XPC services are scoped to the app in which they're embedded。
2. **扩展与主 App 之间用 App Group 共享配置**（本机三个扩展全都用了 `group.*`）。`CFMessagePort` + App Group 是社区最常用的双向通道。
3. **主 App 没启动时扩展也要能干活** → 用 `SMAppService` 注册 login item 做常驻中转。

### 2.3 从 Launcher 继承的资产

工程**完全独立重写**，不共享代码，但两样东西值得直接拷过来：

- **空白 Office 模板**（`blank.docx` / `blank.xlsx` / `blank.pptx`）。docx/xlsx/pptx 是 OOXML（zip 包），0 字节空文件会被 Word/Excel/PowerPoint 判为损坏。Launcher 里这三个最小可用模板 + 生成脚本 `make-blank-templates.sh` 是踩坑换来的，直接复用。
- **发布流水线**：`distribute-free.sh` 里那个**签名校验闸门**（打包后强制校验，被吊销的证书直接中止发布）值得照搬——Launcher 曾经因为签名证书被吊销，导致所有 TCC 授权反复弹窗，这个教训代价很大。

## 三、功能方案

> 市场同类产品的完整功能盘点见 **[竞品功能参考](竞品功能参考.md)**。要点：基础六件套（新建文件 / 剪切粘贴 / 复制到·移动到 / 彻底删除 / 拷贝路径 / 常用目录）已彻底同质化，靠这些做不出差异；真正值得做的是**撤销**和**权限体验**，详见该文档第七节。

### 3.1 菜单设计

#### A. 右键文件（`contextualMenuForItems`，支持多选）

| 菜单项 | 实现要点 | 阶段 |
|---|---|---|
| **复制路径** → 子菜单 | 完整路径 / 文件名 / `cd` 命令 / Markdown 链接 / `file://` URL。`cd` 命令做 shell 单引号引用 | **MVP** |
| **在终端中打开** | iTerm2 / Terminal / 自定义；打开的是**文件所在目录**。`NSWorkspace.open([dir], withApplicationAt:)`，不走 Apple Events | **MVP** |
| 用编辑器打开 | Cursor / VSCode / 自定义，多选并存可排序 | P2 |
| 复制到 / 移动到 | 子菜单列出常用目录 | P2 |
| 压缩 / 解压 | | P3 |
| 彻底删除 | 不进废纸篓 | P3 |
| 显示 / 隐藏 | `chflags hidden` | P3 |
| 查看哈希 | MD5 / SHA1 / SHA256 / SHA512 | P3 |
| 图片转换 | PNG / JPG / HEIC / WebP / ICNS | P4 |

#### B. 右键文件夹（`contextualMenuForItems`）

同上，加上：

| 菜单项 | 阶段 |
|---|---|
| **在文件夹内新建文件** | P2 |
| 解散文件夹（删壳保内容） | P3 |
| 自定义文件夹图标 | P4 |

#### C. 右键空白处（`contextualMenuForContainer`）★ 主场景

| 菜单项 | 实现要点 | 阶段 |
|---|---|---|
| **新建文件** → 子菜单 | 见 3.2。`targetedURL()` 就是当前目录 | **MVP** |
| **复制当前路径** | 同上五种格式 | **MVP** |
| **在终端中打开当前目录** | | **MVP** |
| 用编辑器打开当前目录 | | P2 |
| 显示 / 隐藏隐藏文件 | `defaults write com.apple.finder AppleShowAllFiles` + 重启 Finder | P3 |
| 粘贴（剪贴板里的文件） | Finder 没有真正的剪切，这块是刚需 | P2 |

**上下文取值**：`targetedURL()` 和 `selectedItemURLs()` **只在 `menu(for:)` 内及其 action 内有效**，别的地方调用返回 `nil`。

- 空白处右键：`targetedURL()` = 你右键的那个目录
- 右键文件：`selectedItemURLs()` = 选中项，`targetedURL()` = **所在目录**（注意：与 Apple 文档措辞 "the item that the user Control-clicked" 不符，Open Radar 有实测反例）

→ **判断"是空白还是文件"只能用 `menuKind`，不能靠 `selectedItemURLs` 是否为空**——Finder 在右键空白时是否清空原有选中项，没有文档保证。

### 3.2 新建文件的完整链路（旗舰功能）

```
右键空白处
  → menuKind == .contextualMenuForContainer
  → targetedURL() 拿到目录
  → 从 App Group 读用户配置的类型列表（纯内存，必须快）
  → 返回 NSMenu，每个类型一个 NSMenuItem，tag = 类型索引
  → 用户点击 → action 触发，从 sender.tag 取回类型
  → XPC 把 (目录URL, 类型) 发给 ActionRunner
  → 创建文件（写在 App 侧，非沙盒）
  → 新文件在 Finder 中选中
```

**支持格式**：用户明确要「各种格式」。分三档：

- **纯文本类**（空文件即合法）：`txt` / `md` / `json` / `yml` / `html` / `css` / `js` / `ts` / `py` / `sh` / `xml` / `csv`
- **Office 类**（必须拷模板，不能是 0 字节）：`docx` / `xlsx` / `pptx`
- **自定义**：用户可加任意扩展名，可选绑定模板文件

**两个必须处理好的细节**：

1. **重名绝不覆盖**，自动加序号（`未命名.txt` → `未命名 2.txt`）。Launcher 这里是做对的，照搬语义。
2. **是否进入就地改名状态**：Finder 原生 ⌘⇧N 新建文件夹后能直接改名，是因为那是系统内建行为，第三方做不到。可选做法是创建后用 osascript `select` 让 Finder 选中再发回车——但这**需要「控制 Finder」自动化权限**，为一个锦上添花的效果引入一次 TCC 授权不划算。**建议 MVP 不做，只做「创建 + 选中」**，后续看用户反馈再定。

### 3.3 明确不做

- **云目录兜底**（修饰键+右键自绘菜单）：这是超级右键被迫加的功能，要引入 CGEventTap + 事件监听权限，复杂度翻倍。**先不做，但要在产品说明里如实告知用户 iCloud 目录不生效**——藏着不说，用户会当成 bug 来骂。
- 图片处理、翻译、二维码等边缘功能：先把主链路做扎实。

## 四、关键技术要点

### 4.1 `menu(for:)` 里只允许内存操作

这是**同步阻塞**调用，扩展慢则 Finder 右键菜单卡住甚至假死。社区反复出现的「右键卡顿」根因就在这里，有用户报告过 7 个 FinderSync 扩展进程各占 ~10% CPU。

- 配置必须已经在内存里（App Group 读取提前做，或走 fallback 配置）
- **图标不在菜单渲染时同步解析**，先给占位符再后台缓存
- 任何日志/JSON 读写一律异步

RightClick-Pro 的做法是「暴露全局范围前先装一份 fallback 菜单配置，再后台加载 config/bookmarks」，值得照搬。

### 4.2 菜单项的约束

只支持这些属性：`title`、`action`、`image`、`enabled`、`tag`、`state`、`indentationLevel`、**子菜单**。

- **不支持自定义 `NSMenuItem.view`**——做不了富文本/自定义控件
- **`representedObject` 不可靠**：action 收到的 `sender` **不是**你在 `menu(for:)` 里创建的那个实例，Finder 会复制菜单项，`tag`/`title` 会丢

→ **用整数 `tag` 映射回自己的状态表**。RightClick-Pro 就这么做的。

### 4.3 `directoryURLs` 的真实边界

- **`directoryURLs = nil` 不生效**，不等于「所有目录」。想全局覆盖只能设 `/`。
- **不跨文件系统边界**：设成 `/` **覆盖不到 `/Volumes` 下挂载的卷和 .dmg**。要遍历 `FileManager.default.mountedVolumeURLs(...)` 填充，并监听 `NSWorkspace` 的 mount / unmount / rename 通知动态更新。
- **设 `/` 有冲突风险**：如果有另一个扩展也声明 `/`，「事情会以糟糕的方式收场」（DTS 原话）。不会崩，但菜单/徽章会互相打架。
- **Applications 等目录走 Finder 的另一条代码路径**，扩展在那里不生效，且 DTS 说「不行的名单只会变长」。
- 数量上限：无文档，无实测报告。

### 4.4 其他运行时限制

- 沙盒内**不能 `NSTask` / 起子进程**、不能随意 `NSWorkspace.open`
- `NSHomeDirectory()` 在扩展里返回**容器路径**，不是真实家目录
- `selectedItemURLs()` 拿到的 URL **不带 security-scoped 访问权**，直接读写会 `deny(1) file-write-create`
- **bundle ID 不能含下划线**
- `.appex` 必须在 `Contents/PlugIns` 内，放外面会被 SIP 检查拒绝
- Open/Save 面板会**另开一份扩展实例**

## 五、权限与首次引导

### 5.1 权限清单

| 权限 | 是否必需 | 说明 |
|---|---|---|
| 扩展启用 | ✅ 必需 | 「系统设置 → 通用 → 登录项与扩展 → **文件提供程序**」手动勾选 |
| Apple Events 自动化 | ❌ **不需要** | 路径由 Finder 主动喂（`targetedURL()`），这是相对 Launcher 的一大简化 |
| 辅助功能 | ❌ **不需要** | 只在做「修饰键自绘菜单」兜底时才需要 |
| 写盘 TCC | ⚠️ 首次写桌面/文稿/下载时弹一次 | 常规弹窗，或不弹则引导开启完全磁盘访问 |

### 5.2 首次引导必须做好的三件事

调研里用户抱怨 Top 1 就是「权限/授权地狱」。可以做好的地方：

1. **检测扩展是否启用**：`FIFinderSyncController.isExtensionEnabled`（10.14+），主 App 启动时检查，未启用就给醒目提示。
2. **一键拉起管理面板**：`showExtensionManagementInterface()`，别让用户自己找路径。
3. **自检与修复**：「菜单不出现」是最高频的投诉，引导页要能区分几种原因（扩展没启用 / 扩展被系统杀了 / Finder 需要重启），并给出对应的一键操作（重启 Finder / `pluginkit -e use -i <bundle-id>`）。

**⚠️ 必须避开的坑**：用户直接从 DMG 里双击运行 App（没拖进 `/Applications`）会触发 **App Translocation**，拿到随机路径，TCC 授权直接失效。引导页必须明确要求先拖进应用程序文件夹。

## 六、工程结构

```
LXFinderRight/
├── LXFinderRight/                    # 主 App（非沙盒）
│   ├── App/                          # 入口、生命周期、扩展状态检测
│   ├── Views/                        # 设置界面（侧边栏 + 详情面板）
│   ├── Services/                     # 终端启动 / 编辑器启动 / 复制格式 / 文件操作
│   ├── FileCreation/                 # 类型模型 + 写盘（重名加序号、拷模板）
│   ├── Templates/                    # 空白 Office 模板（从 Launcher 拷，勿手改）
│   └── Shared/                       # App Group 配置读写（与扩展共用）
├── FinderExtension/                  # .appex（沙盒）
│   ├── FinderSync.swift              # menu(for:) 唯一入口
│   ├── MenuBuilder.swift             # 按 menuKind + 上下文构建 NSMenu
│   └── XPCServices/
│       └── ActionRunner.xpc/         # ⚠️ 必须嵌在这里，不是主 App
└── docs/
```

**工程配置要点**：
- 主 App：Developer ID 签名 + 公证，Hardened Runtime，**非沙盒**
- `.appex`：**必须带 `com.apple.security.app-sandbox`**
- 两者共享一个 App Group
- Team ID 必须一致，签名有问题**症状和「扩展不出现」一模一样**，极难排查

## 八、MVP 分期

### MVP —「能用」
用户明确提的三件事，做扎实：

1. 右键**文件/文件夹** → 复制路径（五种格式）+ 用 iTerm/Terminal 打开
2. 右键**空白处** → 新建各种格式文件（文本类 + Office 三件套 + 自定义）
3. 右键**空白处** → 复制当前路径、在终端打开当前目录
4. 设置界面：终端选择、文件类型增删排序、常用格式排序
5. 首次引导：扩展启用检测 + 一键拉起面板 + 自检修复

### P2
多编辑器、复制/移动到常用目录、粘贴（剪贴板文件）、文件夹内新建

### P3
压缩解压、彻底删除、显示/隐藏、哈希、隐藏文件开关

### P4
图片转换、自定义文件夹图标、解散文件夹

| 2 | **右键空白处时 `selectedItemURLs` 是否被清空** | 决定能否用它辅助判断上下文。无文档保证 | 先选中几个文件，再右键空白，打印两个 API 的返回值 |
| 3 | **`directoryURLs = "/"` 的实际生效范围与性能** | 全局覆盖是产品前提。不跨文件系统边界是已知的，实际影响面要实测 | 设 `/` 后测各目录 + 挂载卷 |
| 4 | **菜单首次弹出的冷启动延迟** | 直接决定「右键卡不卡」的口碑 | 杀掉扩展进程后计时 |
| 5 | **macOS 26.1 上扩展加载失败的报告**（ARM 集中报告，26.2 修复） | 影响系统版本兼容策略 | 若有 26.x 实机则实测 |
| 6 | **iCloud 桌面/文稿失效的具体表现** | 桌面是「新建文件」最高频的场景，必须如实告知用户 | 开启 iCloud 桌面同步后实测 |
